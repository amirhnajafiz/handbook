# Processor and Virtual Machine Security

## Quick Description (QD)

In this chapter, we focus on processor and VM security. Moreover, we will see how we can use VMs in security applications.

### Processor Security

Processors operate at multiple privilege levels. At least two levels
are needed, privileged and unprivileged.

- __Ring 0__ is highest privilege (kernel-level)
- __Ring 3__ is lowest privilege (user-level)

OS kernel runs in Ring 0, while user-level code executes in unprivileged mode. Important processor state can be changed only through the execution of privileged instructions.

- Page tables
- I/O devices

As a result, only the kernel code can change critical processor state. Transfers from a lower to a higher privilege level must not be arbitrary (user code must not be able to jump into the middle of kernel code), so crossings are made only through controlled entry points, such as interrupts, exceptions and system calls (traps). These act like request messages to the kernel.

### Virtualization in OSes

Virtualization is the creation of logical instances of physical resources that provide the same functions, without rewriting the software that uses them. Resources to virtualize are:

- CPU
- Memory
- I/O devices

Some resources are shared using high level interfaces (e.g., files) rather than virtualization. Since only the OS can control and manage system resources and share them safely across user-level processes, resources are often virtualized. It is as if a user-level process has an exclusive, private copy of that resource.

### System Virtualization

Creates several virtual systems within a single physical system. A virtual system should still provide privileged instructions, so that OS kernels can run on top. The __VMM (virtual machine monitor, or hypervisor)__ is the software layer providing the virtualization, and VMs run on top of it. The VMM itself runs at the highest privilege level (Ring 0, or the hypervisor mode on hardware with virtualization support), while guest kernels are deprivileged.

#### Process Virtualization

The VM runs a single process (or program) and provides it a virtual execution environment, exposing an application binary interface (system calls) or a language-level instruction set. The VM exists only while that process runs. (e.g., the JVM, which executes Java bytecode)

#### OS or Namespace Virtualization

Having multiple logical VMs that share the same OS kernel. Isolates VMs by partitioning all objects into namespaces. (Docker, vServer)

#### Full Virtualization

The VM supports a complete ISA, including both user and system (privileged) instructions, so unmodified guest OSes can run. (e.g., VirtualBox, VMware)

#### VMM Architectures

There are two types of VMM, __baremetal__ (Type 1) and __hosted__ (Type 2).

#### Type 1 (Baremetal)

The VMM runs on bare hardware.

```txt
|+++++++++++++++++++| |+++++++++++++++++++|
| guest application | | guest application |
|+++++++++++++++++++| |+++++++++++++++++++|
===========================================
|++++++++++++++++++|
|  multi guest OS  |
|++++++++++++++++++|
===========================================
|+++++++++++++++++++|
|        VMM        |
|+++++++++++++++++++|
===========================================
|+++++++++++++++++++|
|   host hardware   |
|+++++++++++++++++++|
```

#### Type 2 (Hosted)

The VMM runs as an ordinary application inside host OS.

```txt
|+++++++++++++++++++| |+++++++++++++++++++|
| guest application | | guest application |
|+++++++++++++++++++| |+++++++++++++++++++|
===========================================
|++++++++++++++++++|
|  multi guest OS  |
|++++++++++++++++++|
===========================================
|+++++++++++++++++++|
|        VMM        |
|+++++++++++++++++++|
===========================================
|+++++++++++++++++++++++|
| host operating system |
|+++++++++++++++++++++++|
===========================================
|+++++++++++++++++++|
|   host hardware   |
|+++++++++++++++++++|
```

#### Key Issues in CPU Virtualization

- Protection levels.
- Requirement for efficient virtualization (Popek and Goldberg). Privileged instructions trap when executed from user-level. Sensitive instructions are the ones that affect important system state. Therefore, if all sensitive instructions are privileged, the VMM can use the efficient __trap and emulate__ approach: the guest kernel runs deprivileged, and every sensitive instruction traps into the VMM, which emulates it.
- For classic x86, not all sensitive instructions are privileged, so trap and emulate alone does not work.

#### Virtualization Approaches

- __Full virtualization__ using binary translation: needs to disassemble the binary, identify sensitive instructions and patch them. Relies on dynamic disassembly and translation in order to make disassembly tractable, and to support dynamic changes to code. (like early VMware, or QEMU in its software emulation mode)
- __Paravirtualization__: the guest OS is modified to run on the VMM and uses hypercalls instead of sensitive instructions. It is no longer 100% interface compatible, but has better performance. (like Xen)
- __Hardware-assisted virtualization__: sensitive guest operations trap to the VMM without binary translation or paravirtualization (Intel VT-x, AMD-V). The CPU has two modes: the hypervisor executes in host mode, and all VMs execute in guest mode. (most VMMs today, e.g., KVM)

#### Memory Virtualization

Access to MMU needs to be virtualized, otherwise guest OS may directly access physical memory and subvert VMM. Physical memory is divided among multiple VMs with two levels of translation in Guest OS and VMM.

- Guest OS: guest virtual addr $\to$ guest physical addr
- VMM: guest physical addr $\to$ machine addr

A __shadow page table__ avoids the 2-step translation: it maps guest virtual addresses directly to machine addresses, and is the one the hardware MMU uses. When the guest attempts to update its own page table, the VMM intercepts the update and emulates its effect on the corresponding shadow page table. (Newer CPUs do the two-level walk in hardware, e.g., Intel EPT and AMD NPT.)

#### I/O Virtualization

The VMM intercepts the guest's I/O-performing instructions and performs the necessary actions to emulate their effect. This emulation leads to low performance for most I/O operations, compared to CPU and memory, where most guest instructions run directly with little extra work.

### VM Security Applications and Concerns

#### Security Applications

VM technology provides strong isolation that is necessary to run malware
without undue risks. (Strong resource isolation and snapshot/restore features)

- __Honeypot systems__
- __Malware analysis__

Basically, VMs limit the damage malware can cause and keep the guest OS in a known state. Also, a VMM can protect against compromised guest OSes, by running malware and rootkit detection techniques in the VMM, or by enforcing security properties from within the VMM.

#### Rootkit

A rootkit is a set of software tools that enable an unauthorized user to gain control of a computer system without being detected.

#### Security Challenges in Virtualized Environments

Since virtualization leads to __co-tenancy__, it brings challenges.

- VMs belonging to distinct principals use the same hardware. Therefore, it needs strong isolation.
- It provides increased opportunities for side-channel attacks.
- Denial of service is also hard to prevent.

#### Docker Security

It uses __namespaces__ (what a container can see) and __cgroups__ (how many resources it can use) to isolate its containers. It also has a container infrastructure and services (__docker daemon__). Containers can share files with the host OS, but this can be dangerous since it can allow the root user in a container to change critical host OS files.

#### Docker Attack Vectors

- Shared kernel: it is using same OS kernel across different containers. Any kernel vulnerabilities may be exploited.
- The Docker daemon normally runs as root (unless rootless mode is used), so malicious processes may abuse this privilege.
- Apps running within Docker can reach the host through shared folders. Also, root processes inside a container may be able to perform privileged operations on the host if the container is misconfigured.

#### Docker Security Practices

- Avoid root privilege (run as a non-root user, or use rootless mode).
- Limit further using Linux capabilities (see [Security Policies](06_policies.md)).
- Use seccomp-bpf to limit system calls that can be made by processes within the container.
- Avoid using untrusted software.
