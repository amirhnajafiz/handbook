# Operating System Security

## Quick Description (QD)

This chapter focuses on OS security and processes. Mostly talking about UNIX systems.

### UNIX Intro

User level is a set of processes, the kernel does not place requirements
on which processes should run. Command shell is one such process, and there can be many such command shells. Programs can spawn other programs, orchestrate them to achieve higher level goals. Interconnect programs using pipes. Everything is a file in operating system. Every device is a file. File permissions provide a universal access control mechanism.

System Architecture:

```txt
the users
-------------------------------------
shell and commands, compilers and interpreters, system libraries
=====================================
system-call interface to the kernel
=====================================
signals terminal handling character I/O system terminal drivers
file system, swapping block I/O, system disk and tape drivers
CPU scheduling, page replacement, demand paging, virtual memory
=====================================
kernel interface to the hardware
=====================================
terminal controllers, terminals | device controllers, disks and tapes | memory controllers, physical memory
```

File System organization:

```txt
/vmunix
/bin : contains binaries
/boot : contains files required for starting the system
/dev : contains device files
/etc : everything to configure
/home : user's personal directories
/lib : system libraries
/media : external storage mounted
/mnt : where you manually mount storage devices or partitions
/opt : optional, add-on application software
/proc : virtual directory exposing process and kernel information
/root : home directory of superuser
/tmp : used for storing temporary files
/sbin : similar to /bin, but has system administration binaries (mostly for the superuser)
/sys : virtual directory exposing information about devices and drivers
/var : variable data such as logs, spools and caches
```

### Processes

Process is a program in execution which has a __pid__, __owner__, __group__, and other attributes. Processes have separate virtual address spaces.

This memory isolation provides the basis of security:

- a process cannot access the memory of other processes.
- access to kernel memory controlled by page permissions.
- read/write/execute permissions set at the granularity of a page.

#### Virtual Memory

Each process has a logically separate address space. Memory is organized into pages (typically 4KB). Swap space is disk space for backing up pages that don't fit into physical memory. The processor raises an exception (a page fault) when a page is not in physical memory, and the OS handles the exception transparently to bring the page into memory.

#### Virtual Memory Allocation

May be OS initiated or be requested by a process (using mmap, mprotect).

#### Process Control Block (PCB)

Contains all process state that the OS needs to manage.

- register values
- uid, gid, current directory, ...
- open file table, file descriptors are indices into this table

#### `fork` System Call

When using the `fork` system call, the child inherits all its parent's attributes. So the child is an exact copy of the parent, except for the return value of the syscall (zero for the child, the pid of the child for the parent). Copying memory is expensive, so modern kernels use copy-on-write pages. On Linux, `fork` is implemented on top of `clone`, a generalization that allows fine control over what is shared between parent and child.

#### `execve` System Call

Used to replace the calling process with a new program. When using this system call, all of the memory is overwritten. But the pid and open file descriptors are kept (except those marked close-on-exec).

#### `exit` and `wait` System Calls

Processes return a status code when they exit. The parent receives this status when it waits on a child. A child cannot be fully removed until the parent collects this code, otherwise it stays as a zombie.

#### Process Scheduling

Processor time is split across running processes. Scheduler is responsible for stopping one process and giving a turn to the next process.

#### Process Ownership

Each process has an __owner (uid)__ and a __group (gid) owner__. A root process can change its uid and gid. By default, a process inherits the uid of its parent. The __setuid__ permission bit on an executable allows a uid change on `execve`: the process assumes the uid of the executable file's owner. This allows normal users to access features that require privilege (e.g., `passwd`, `sudo`).

#### Userids

- __Effective userid__: all access checks use this id.
- __Real userid__: the user that logged in. After executing a setuid executable, the real user remains the same but the effective user becomes the file's owner (e.g., root).
- __Saved userid__: lets a process temporarily drop privileges and later restore them; the effective uid is saved here when it is changed.

An unprivileged process is allowed to switch its effective userid between its real and saved userids. For fine grained control over the different ids, use:

- `seteuid`
- `setreuid`
- `setresuid`

#### Userids vs Usernames

The file `/etc/passwd` maps userids to usernames. Similarly, group names are specified in `/etc/group`. Note that `/etc/passwd` is a public database, however, password hashes are in `/etc/shadow`, which can be read only by root.

### File System

A __File__ is simply a sequence of bytes. __Directory__ is a special file that contains information about the location of files. __Path__ is a sequence of directory names followed by a file name. File implementation is done by using __Inodes__.

```txt
| mode      |
| owners    |
| timestamps |
| size      |
| direct block  | => | data |
| single direct | => | A | B | data | data | => | block A |, | block B |, ...
```

#### Key System Calls for Files

- open: returns a file descriptor for reading/writing the file
- read, write
- mmap : map part of a file
- lseek : move file pointer to different places
- chmod
- chown

### Link vs File

__Hard link__ is like a file name; it points to the actual file. __Symlink__ is a special file that is interpreted as the name of another file/dir. Path-to-file translation involves dereferencing many links. OS limits the number of symlinks traversed to prevent infinite loops during lookup.

#### Key System Calls for Links and Directories

- rename
- link, unlink
- mkdir, rmdir

### Interprocess Communication

- __Pipe__ is a unidirectional communication channel. The `pipe` syscall returns a pair of fds: the read end in `fd[0]` and the write end in `fd[1]`.
- __Socketpair__ is similar, but allows bidirectional communication: what is written to `fd[0]` can be read from `fd[1]` and vice versa.

#### How Does I/O Redirection Work?

Application needs no special code to support redirection. By default, all applications read from fd 0 (stdin), write to fd 1 (stdout), and display errors on fd 2 (stderr).

To redirect input from a file, the shell opens the file and makes a copy of its fd as fd 0:

```c
dup2(file_fd, 0); // fd 0 now refers to the file
```

To create a pipeline (`cat | wc`), the shell creates a pipe with endpoints `fd[0]` and `fd[1]`, and forks children that inherit these fds. The writer (`cat`) uses `dup2(fd[1], 1)` and closes `fd[0]`; the reader (`wc`) uses `dup2(fd[0], 0)` and closes `fd[1]`.

#### Socket Communication

Sockets may be used by servers or clients.

- Server steps: `socket` $\to$ `bind` $\to$ `listen` $\to$ `accept` $\to$ `read`/`write`
- Client steps: `socket` $\to$ `connect` $\to$ `read`/`write`

### Signals

A signal is an exception-related control-flow mechanism which is modelled after hardware interrupts. A signal can suspend current processing, and gets handled by a signal handler. `SIGKILL` and `SIGSTOP` cannot be caught or ignored.

#### Key Signals

- process control: SIGKILL, SIGTERM, SIGINT, SIGQUIT, SIGSTOP, SIGTSTP, SIGCONT
- illegal memory access: SIGSEGV, SIGBUS
- low-level errors: SIGFPE, SIGILL, SIGABRT
- child exited: SIGCHLD
- timer interrupt: SIGALRM
- input/output related condition: SIGPIPE, SIGHUP
- bad system call: SIGSYS

#### Signal Generation, Delivery and Handling

There are two types of signals, sync and async. A sync signal is caused by program execution, while an async signal is generated due to external events.

Handlers are installed using the `signal` or `sigaction` syscalls (prefer `sigaction`). By default, a handler runs on the process stack, but a separate stack can be set up with `sigaltstack`. Besides a handler function, a signal can be set to:

- `SIG_IGN` (ignore)
- `SIG_DFL` (default action)

Signals can be blocked, but standard signals are not queued: if the same signal arrives several times while blocked, it is delivered only once. Handlers need care because they can interrupt the program at any point, so they should only call async-signal-safe functions.

### Notes and Comments

- The __sticky bit__ is a permission bit that protects the files within a directory. If the directory has the sticky bit set, a file can be deleted only by the file owner, the directory owner, or by a privileged user.
